# Adding a New Command

This repo keeps one canonical skill source: `claude/skills/<name>/SKILL.md`.
Codex and pi outputs are generated by installer/compiler scripts. Add a command
only when the workflow is repeatable enough to encode as deterministic prose,
and make it fit the active OpenSpec lifecycle unless it is a general utility.

Before adding or reshaping workflow commands, read:

- [`openspec-lifecycle.md`](openspec-lifecycle.md) — lifecycle states and
  command ownership;
- [`openspec-conventions.md`](openspec-conventions.md) — artifact schema,
  proof matrices, Debt Friction, runtime logs, and notebook conventions.

## When to add one

Add a command when you keep hand-walking agents through the same checkpoints and
those checkpoints are stable enough to become a skill. Do not add commands for
one-off tasks, exploratory work, or workflows whose steps change every run.

New workflow commands should belong to the active OpenSpec flow (`openspec-*`).
Non-workflow utilities are allowed when they are generally useful and do not
introduce another lifecycle state model.

Archived legacy workflow sources live under `archive/skills/legacy-epic/` for
provenance only. Active installers do not scan that archive.

## File checklist

A new command called `<name>` uses the Claude hyphenated form and requires:

1. `claude/skills/<name>/SKILL.md` — canonical Anthropic Skill format.
2. Optional `pi-fragments/<name>.md` — pi-specific append fragment, or a full
   replacement if the fragment starts with YAML frontmatter (`---`).

Do not add files under `codex/skills/`: generated Codex `SKILL.md` files and
`agents/openai.yaml` policies are produced by `scripts/install-codex.sh`.

## Claude Skill template

```md
---
name: <name>
description: <one-sentence description that ends with "Use when ...">
disable-model-invocation: true
argument-hint: "<arg-shape>"
allowed-tools: Read Edit Write Grep Glob Bash
---

# <Title>

<one paragraph summary>

Argument: `$ARGUMENTS` — <what the user passes>.

## Workflow
1. ...
2. ...

## Final response
<what the operator should see when the command finishes>
```

### Frontmatter rules

- `name:` must match `claude/skills/<name>/`.
- `description:` describes both what the skill does and when to use it.
- `disable-model-invocation: true` is the default for this repo. These are
  operator-driven workflows, not background capabilities Claude should auto-run.
- `argument-hint:` is shown in the slash-command picker; keep runtime argument
  shapes aligned.
- `allowed-tools:` lists only what the skill actually uses. Prefer narrow
  `Bash(...)` patterns when practical. Read-only commands should not list
  `Edit` or `Write`.

## Body conventions

- Lead with a concise summary, then `Argument:` and a clear workflow.
- Use `## Phase N — <name>` headings for multi-step workflows. Lint checks phase
  parity between canonical Claude and generated Codex output.
- Make source-of-truth hierarchy explicit. Live repo evidence wins over stale
  assumptions; OpenSpec artifacts are the workflow authority for lane/status.
- Keep command authority narrow. A plan-review command should not implement; a
  feedback command should not approve plans; a looper should not write lifecycle
  artifacts directly.
- Use explicit checkpoints for irreversible or high-blast-radius actions.
- For planning/implementation commands, encode proof-first planning and
  red-first execution. If red-first can be infeasible, require a written
  exception path.
- For looper/orchestrator commands, preserve delegated ownership: launch fresh
  sessions and, only when the owning skill permits optional carried context,
  copy bounded sourced records containing exactly `Ref`, `Purpose`, `Expected
  anchors`, and `Lookup` (selected content, not a retrieval instruction). Supply
  non-sourced coordination separately as at most one neutral ops payload; never
  disguise it as a sourced record. Document hard stops and no-progress gates,
  and avoid persuasive verdict framing. Oblivious review commands must not
  receive carried notebook, operational, summary, or prior-chat context.
- End with `## Final response` describing the operator-facing result. Every
  active OpenSpec workflow command must include exactly one canonical
  next-action form:

  ```text
  Suggested next action: <exact command | operator action | wait | None>
  ```

  or, only when both workflow routes are valid:

  ```text
  Suggested next action:
  - Converge wrapper: <exact command | operator action | wait | None>
  - Non-looped pass: <exact command | operator action | wait | None>
  Choose one; do not run both.
  ```

  Resolve command arguments where possible. Use an operator action for a choice
  or manual intervention, `wait` when progress depends on an external event,
  and `None` when no workflow action remains. Do not introduce competing
  `Next Action` or `Suggested next step` fields.

## Pi fragments and notebooks

Pi fragments should add runtime primitives only when the base skill needs
pi-specific behavior:

- use `spawn` for focused probes or fresh child-agent passes;
- use optional notebook pages for durable, sourced research or neutral ops notes; non-Pi runtimes continue canonically without them;
- treat notebook pages as orientation, not lifecycle authority;
- verify material notebook claims with direct reads/search before edits or
  status transitions in commands that allow notebook context;
- do not pass notebook context into oblivious implementation review.

Use only canonical repository-qualified stable families:

- `openspec-research-<repository_key>-<initiative>-<story>`
- `openspec-ops-<repository_key>-<initiative>-<story>`
- `openspec-plan-research-<repository_key>-<initiative>-<story>`
- `openspec-plan-ops-<repository_key>-<initiative>-<story>`
- `openspec-plan-review-research-<repository_key>-<initiative>-<story>`
- `openspec-review-<repository_key>-<initiative>-<story>`

Repository-key-v1 is defined normatively, in full, by
`docs/openspec-conventions.md`. Commands must apply the
exact normative repository-key-v1 contract rather than copy or invent a
runtime-specific normalization or hash
recipe. Locally, a missing/invalid identity or reroot key drift skips or fails
closed only for the selected optional notebook operation; canonical artifact
work continues, and checkout-derived or per-run keys remain forbidden.

Shared stable pages have one coordinator writer. Every write is whole-page
read-modify-write preserving active and unrelated entries; retire/compact
in-page with provenance. A converger may read the whole page and pass only selected copied records, each
with exactly `Ref`, `Purpose`, `Expected anchors`, and `Lookup` (selected content,
not a retrieval instruction), plus at most one separate neutral-ops payload. Its child neither reads/writes notebooks nor spawns recursively; it
researches inline and returns proposals. Use in-page retirement and in-page compaction, never page
deletion, reset, topic assumptions, or renaming selectors.

Current Pi spawn exposes notebook tools and automatic previews, so it does not
establish isolation for supplemental implementation-review orientation. Skip
that optional spawn and review canonical artifacts/live paths directly. Retain
token/sentinel checks only for runtimes that independently prove an isolated
child boundary; child self-attestation is not proof.

Do not store raw transcripts, private deliberation, or broad scratch logs.

## Generated Codex skills

Codex discovers skills from `.agents/skills/` per project root or
`~/.codex/skills/` for user-level installs. This repo generates those skill
directories instead of committing them:

```text
~/.codex/skills/<name_with_underscores>/
├── SKILL.md
└── agents/
    └── openai.yaml
```

`scripts/install-codex.sh` compiles each canonical Claude skill by:

1. preserving the canonical body unless a runtime argument rewrite is required;
2. converting directory and frontmatter `name:` from kebab-case to snake_case;
3. rewriting `$ARGUMENTS` into Codex named-variable contracts for skills that
   accept arguments;
4. writing `agents/openai.yaml` with `allow_implicit_invocation: false`.

Generated output rules:

- generated Codex `name:` matches the snake_case directory;
- phase headings match the Claude source when present;
- runtime-specific differences are explicit in compiler code, fragments, and
  lint expectations.

## Runtime pairing

Base name normalization is hyphen ↔ underscore:

- canonical Claude: `openspec-story-claim`
- generated Codex: `openspec_story_claim`
- generated pi: `openspec-story-claim`

The lint script checks generated counterparts automatically. Runtime-only
exceptions must be explicit; do not ship a singleton silently.

## Lint and ship

```bash
bash scripts/lint.sh
```

If lint exits 0, the command set is internally consistent. If it fails, fix the
reported issue rather than bypassing the check; those are the same invariants a
reviewer would call out.
